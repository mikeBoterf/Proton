# Elytra-on-Proton diagnostic tests

Standalone tests that accompany `../wardogs-elytra-proton-findings.md`. They isolate
individual things Elytra's `elytraldrfs` driver does at the point it fails
(`WD-L014`). They touch **nothing** belonging to Elytra; they exercise Wine's own
primitives with our own data.

> **Read the limits before citing these.** The crypto tests below are weaker evidence
> than earlier revisions of the findings document claimed, and the companion review
> ([`../wardogs-elytra-independent-review.md`](../wardogs-elytra-independent-review.md))
> was right to say so. See *What these do and don't establish*.

Build with the repo's toolchain (`nix develop`, then MinGW), run under the built
Proton (`steam-run <compat-tool>/proton runinprefix <exe>`).

| File | Exercises |
|---|---|
| `bcrypt_inplace_test.c` | Wine's AES-128-CBC in-place decrypt, round-tripped at 48 B, 1 MB, and the full 52.7 MB. |
| `ecdsa_test.c` | Wine's ECDSA P-384 / SHA-384 verify — accepts valid signatures, rejects corrupted ones. |
| `buftest.c` (driver) + `buftest_user.c` | A 52.7 MB `METHOD_BUFFERED` IOCTL delivered to a driver, driver-side hash vs user-side hash — tests Wine's large-IOCTL marshaling. |
| `padding-matrix.c` | The Windows conformance matrix: 4 padding cases x 2 providers x in-place/separate. Compares Wine against measured Windows semantics (status, `pcbResult`, IV advance). Ported from the Windows control run. |
| `fixtures/` | Ciphertext generated by **openssl**, not by Wine. Regenerate with `fixtures/generate-fixtures.sh`. |

### Running the matrix

```sh
x86_64-w64-mingw32-gcc -O2 -D__USE_MINGW_ANSI_STDIO=0 padding-matrix.c -o padding-matrix.exe \
  -nostdlib -fno-stack-protector -Wl,--entry,mainCRTStartup -lbcrypt -lkernel32 -lucrtbase

# run from this directory so fixtures/ resolves; prefix must live under $HOME
# (steam-run mounts /tmp as a fresh tmpfs)
STEAM_COMPAT_DATA_PATH=$HOME/.cache/wardogs-padding-test/pfx \
STEAM_COMPAT_CLIENT_INSTALL_PATH=$HOME/.steam/steam \
  steam-run ~/.steam/steam/compatibilitytools.d/wardogs-elytra/proton run ./padding-matrix.exe
```

Output is `padding-matrix.txt`; exit 1 means at least one Windows expectation differs.
Captured runs are kept in `results/`.

## What these do and don't establish

**`buftest` is the strongest of the three.** It computes the hash independently on
each side of the boundary, so a match is real evidence that Wine's large-IOCTL
marshaling delivers the buffer intact.

**`ecdsa_test.c` has the same structural weakness as the AES round-trip:** it signs
and verifies through Wine, so it shows self-consistency rather than agreement with
Windows. It does at least return non-zero on failure.

**`bcrypt_inplace_test.c`'s round-trip section is still self-referential by design.**
`test_mode()` encrypts *and* decrypts through the same Wine backend, which shows
self-consistency, not equivalence to Windows — an implementation wrong in a symmetric
way passes cleanly. Keep it for regression value, but it cannot support a claim that
Wine's AES is "bit-for-bit correct". The `test_fixture()` cases are the ones with
evidentiary weight: their ciphertext comes from openssl.

Three defects that previously made this file misleading have been fixed — they are
recorded here because the retracted verdict in
[`../wardogs-elytra-postmortem.md`](../wardogs-elytra-postmortem.md) rested on them:

- it never passed `BCRYPT_BLOCK_PADDING`, so the padded path — the one reportedly
  failing — was never exercised;
- `main()` returned `0` unconditionally and discarded every `test_mode` result, so the
  exit code could not report failure;
- nothing in it was generated outside Wine.

**Closed since:** `fixtures/` now holds openssl-generated ciphertext,
`bcrypt_inplace_test.c` exercises `BCRYPT_BLOCK_PADDING` against those fixtures and
returns a meaningful exit code, and `padding-matrix.c` covers the full Windows
semantic matrix. **Still open:** an exact-size (55,275,056 byte) padded fixture — the
matrix uses 48-byte cases.

Build examples:

```sh
# user-mode tests
x86_64-w64-mingw32-gcc bcrypt_inplace_test.c -o bcrypt_t.exe -lbcrypt
x86_64-w64-mingw32-gcc ecdsa_test.c          -o ecdsa_t.exe  -lbcrypt

# test driver (needs the ddk include dir on the path)
DDK=$(dirname $(find /nix/store/*mingw32-gcc*/x86_64-w64-mingw32/sys-include/ddk/wdm.h | head -1))
x86_64-w64-mingw32-gcc -O2 -nostdlib -shared -o buftest.sys buftest.c -I"$DDK" \
  -Wl,--subsystem,native -Wl,--entry,DriverEntry -Wl,--image-base,0x140000000 -lntoskrnl
x86_64-w64-mingw32-gcc -O2 buftest_user.c -o buftest_user.exe
# load: sc create BufTest type= kernel binPath= C:\...\buftest.sys && sc start BufTest
```

## Status

The buffer arrives intact, and Wine's padded in-place decrypt handles externally
generated ciphertext correctly at 48 bytes — yet the real driver still fails.

**The candidate readings have been decided by measurement, not by these tests.** A
`WINEDEBUG=+bcrypt` trace of a real launch shows the driver making one padded,
in-place `BCryptDecrypt` of 55,275,056 bytes (`dwFlags = 0x1`) and then tearing down
with **no signature verification** — so the failure is at module decryption, before
anything that could attest the environment. See *Two competing readings* in the
findings document.

**Why** the decrypt fails is still unknown. These tests do not answer it: they cover
48-byte fixtures, and nothing here reproduces the retail call's key, IV or 52.7 MB
input.

Whatever the cause, this project does not fake the kernel or forge attestation.
